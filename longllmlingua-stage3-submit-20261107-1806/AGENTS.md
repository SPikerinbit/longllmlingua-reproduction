## 3. 正式范围与实验口径

- 数据：NaturalQuestions，多文档 QA，每题 20 篇文档；答案文档位置为第 1、5、10、15、20 位，对应上游索引 0、4、9、14、19。
- 方法：原始提示、BM25、LLMLingua、LongLLMLingua。原始提示只运行一次，不因 2x/4x 设置重复付费调用。
- 压缩设置：2x、4x。定义为原始完整提示 token 数 / 压缩后完整提示 token 数；记录目标预算与实际比值，不能把库的 rate 或 ratio 参数直接当作测量结果。
- 五种位置的主实验关闭文档重排序；重排序另设实验，不与未重排序主表混合。
- 压缩模型显式指定 LLaMA-2-7B-Chat，获取授权、权重 revision、精度、分词器与依赖版本在第一阶段登记。LLMLingua 与 LongLLMLingua 使用同一压缩模型。
- 问答使用小组可用的一个 API 模型，第一阶段验证后固定模型标识、可取得的版本信息、提示模板、最大生成长度和生成参数。支持时使用 temperature=0；不支持时记录实际设置。
- 指标复用上游 `best_subspan_em` 及其首行回答处理。需要调整时新增指标，不覆盖原口径。
- 输入、输出 token 使用固定的问答模型分词器计数；另外记录 API 返回的实际用量。两者不混为同一口径。若模型无可用本地分词器，第一阶段明确计数方案并固定，报告其局限。
- 论文历史问答模型是 GPT-3.5-Turbo-0613 / GPT-3.5-Turbo-16k-0613，并包含 LongChat-13B-16k。当前 API 替代属于方法级复现，不能声称严格重现历史数值。
- LongBench、ZeroSCROLLS、MuSiQue、LooGLE、完整 NQ 2,655 题和其他论文基线均为扩展，不作为本轮必需验收项。

### 固定数据规模

| 集合 | 问题数 | 位置数 | 用途 |
| --- | --- | --- | --- |
| smoke | 20 | 5 | 调通与阶段一、二验收 |
| pilot | 100 | 5 | 排错、费用与时长估算 |
| main | 500 | 5 | 正式主实验与第四阶段消融 |

固定随机种子 42，从各位置均存在的共同问题集合生成一次打乱列表，前 20/100/500 个构成嵌套集合；保存稳定问题 ID、清单和生成过程。问题 ID 由规范化问题及答案集合生成稳定摘要，遇重复时核验合并或报错，不使用不同位置的行号对齐。

各位置、方法与预算复用同一集合，不根据得分更换样本。答案、gold 标记与答案位置只用于数据构造、验收和评分，不进入压缩、BM25 排名或问答输入。五位置的同一问题保持文档集合一致；变动只来自上游位置构造。

### 论文参数对照

本地论文记录：V100 32GB、PyTorch 1.13.1、LLaMA-2-7B-Chat、迭代段长 200、粗细粒度控制系数 k=2、动态压缩参数 0.3、指令与问题的预定义压缩参数 0.85/0.9。restrict 提示为 `We can get the answer to this question in the given documents.`。

这些是论文设置，不是已完成的环境配置。第二阶段逐项核对固定官方版本是否暴露对应参数，记录实际映射；不得把文档默认值或名称相近的参数直接视为等价。无法直接表达的设置须说明实现方式或差异。

## 4. 四阶段任务与交接

依赖链：**第一阶段：数据与基线 → 第二阶段：压缩方法 → 第三阶段：主实验 → 第四阶段：消融与效率解释**。

每阶段均负责本阶段代码、验证、实验产物、报告和答辩材料。每人解释自己的方法选择与结果；成员四汇编最终报告，不承担其他三人的全部文稿。阶段三可提前准备调度与统计，阶段四可提前设计消融矩阵；正式运行必须引用已验收的上游版本。

### 第一阶段：成员一——数据、实验底座与基线

**要回答的问题：如何建立可信、可复用的比较起点？**

输入：本地论文、官方代码与数据源、服务器权限及可调用 API。

任务：
1. 固定来源版本，建立论文—设置—代码的对照；登记服务器、模型和依赖。
2. 实现数据下载/校验、五位置对齐、固定 ID 与 smoke/pilot/main 清单。
3. 固定问答模板、API 配置与生成参数，提供统一调用、基本失败记录及预测缓存。
4. 实现原始提示与 BM25 基线。BM25 仅按问题评分，按相关性选取满足预算的文档或片段，选完恢复原文档顺序；固定分词和预算策略并记录与论文的差异。
5. 接入上游评分，输出逐样本记录和轻量汇总，完成阶段一说明与答辩材料。

产物：可重建环境、数据清单、基线代码、API 配置示例、真实 smoke 结果、运行日志、接口说明与交接记录。

验收：20 题 × 5 位置，原始提示及 BM25 的 2x/4x 设置均完成真实问答和评分；BM25 同时记录实际压缩率；无未解释缺失记录。另一人可按说明复现入口并使用已有缓存重新评分。

答辩贡献：数据构造、位置偏置设计、基线公平性、结果可重复性。详细执行清单见 `docs/stage1-checklist.md`。

### 第二阶段：成员二——压缩方法与机制验证

**要回答的问题：LongLLMLingua 如何保留与问题相关的信息？**

输入：第一阶段已验收的工程、数据清单、API 与结果约定。

任务：
1. 在统一入口接入 LLMLingua、LongLLMLingua；固定版本实际函数签名是适配依据。
2. 核对问题感知粗粒度评分、细粒度压缩、动态预算、restrict 提示、重排序及子序列恢复的论文含义和实现。
3. 暴露独立配置开关；恢复在问答之后执行，保留恢复前后回答。
4. 输出文档评分、保留文档、token 预算和关键文本变化的追踪样例，验证开关确实改变对应机制。
5. 补充必要的机制测试、方法说明及本阶段答辩材料。

产物：统一压缩适配、配置、机制开关、过程追踪、压缩前后案例、论文参数映射与差异表。

验收：沿用 smoke 集，两个压缩方法在 2x/4x 均可运行；每个开关有行为证据；无 gold 泄漏；完整方法输出能直接交给第三阶段。未实现模块如实标记，不使用无效开关冒充消融。

答辩贡献：算法机制、论文与代码对应关系、复用和自主工作的边界。

### 第三阶段：成员三——主实验与位置偏置评估

**要回答的问题：压缩是否改善回答效果并节省输入？**

输入：阶段二验收版本、固定数据集合、方法接口与模型配置。

任务：
1. 将第一阶段的基本缓存完善为批量调度、限流重试、断点续跑、失败清单和覆盖率检查。
2. 先完成 pilot，估算费用与时长；冻结正式配置后执行 main。
3. 完成原始提示及其余三种方法 2x/4x 的五位置实验；复用相同配置的已有预测。
4. 生成主表、位置曲线、质量—实际压缩率图及代表性成功/失败案例。
5. 按问题 ID 配对比较，bootstrap 时以问题为单位重采样，五个位置一起保留；固定种子 42，2,000 次，报告 95% 区间及分母。

产物：批量运行与汇总代码、逐样本预测、配置、覆盖率与失败清单、主表、图表、主实验报告及答辩材料。

验收：main 共 500 题 × 5 位置；相同样本、问答模型、模板与指标。缺失/失败显式报告，成对比较使用共同成功样本并注明覆盖率，未补齐前不标记正式矩阵完成。图表可从保存的结果独立重建。

答辩贡献：实验控制、位置敏感性、统计证据与结论可靠性。

### 第四阶段：成员四——消融、效率与综合解释

**要回答的问题：收益来自哪些机制，是否值得额外开销？**

输入：阶段二的机制开关、阶段三的主实验结果与冻结配置。

任务：
1. main 集、2x、五位置，分别移除问题感知粗粒度、问题感知细粒度、动态预算、restrict 提示和子序列恢复，一次只改一个机制。
2. 另加文档重排序实验，与主实验关闭重排序的完整方法对照；不把已关闭的重排序再当作移除消融。
3. 复用完整方法既有预测；恢复消融复用同一原始回答，分别评分恢复前后结果，不重复调用 API。
4. 分别测量压缩、问答、恢复、端到端耗时、压缩 GPU 峰值显存、API 实际 token 用量；在相同服务器、并发和样本下比较，预热后报告 p50/p95。缓存命中用时与真实推理用时分开，API 网络波动如实说明。
5. 分析失败类型、论文差异、效率权衡与局限；汇编各人的材料及可演示流程。

产物：消融配置与结果、效率表、错误归因、最终报告、汇编后的答辩材料和演示说明。

验收：每项消融仅变动目标机制；收益和代价可追溯到配置、日志、预测与样本。未取得实时单价时只报告 token 用量，不编造金额或沿用历史价格。

答辩贡献：机制作用的实验证据、效率权衡、复现边界与适用条件。

## 5. 工程接口与结果约定

第一阶段已按以下约定实现数据、基线、问答、缓存与评分。实际入口见 README.md，第二阶段方法接口见 docs/stage1-implementation.md；压缩及恢复算法仍待成员二实现。

- 数据层保留稳定问题 ID、问题、答案列表、有序文档、文档 ID 和 gold 位置；方法层只接收问题、文档文本/标题/普通 ID 及必要指令。评分字段单独传递给评估器。
- 方法入口：统一接收可见样本和方法配置，返回完整问答提示、预算和方法元数据。四种方法都进入同一个问答与评分流程。
- 恢复入口：接收原提示、压缩提示、原始模型回答，输出恢复后回答及耗时。缓存须保留原始模型回答。
- 逐样本结果至少包含：问题 ID、位置、集合、方法、压缩预算、完整配置摘要、上游与工程版本、压缩/问答模型和版本、提示或其受控存储位置及摘要、原始/压缩 token、API 输入/输出 token、各阶段耗时、恢复前后回答、对应评分、状态和错误。
- 问答缓存标识覆盖样本可见内容、完整提示、模型、生成参数、API 服务标识和相关配置；压缩缓存另覆盖压缩模型及方法版本。密钥不进入摘要或日志。恢复配置变化可以复用原回答，但须重新恢复和评分。
- 运行状态区分成功、失败和跳过；记录可重试原因，续跑不重复调用已成功且标识一致的请求。
- 配置以文件保存；运行记录追加，汇总文件可重建，禁止只保留最终平均分。

建议工程职责：`src/` 实现数据、提示、方法、API、评分和记录；`configs/` 保存配置；`scripts/` 提供下载、运行和汇总入口；`tests/` 验证关键行为；`reports/` 保存轻量结果及材料。实际入口在实现后写入 README，禁止记录虚构命令。

## 6. 必要验证与完成标准

- 五位置问题集合、答案与文档集合一致，gold 实际位置正确，集合规模符合清单。
- 进入算法和 API 的字段不含答案、gold 标记、答案位置或其他评估标签。
- 评分与固定上游流程一致，覆盖大小写/标点、多答案、首行截断等案例。
- 改提示、模型或生成参数会使相应缓存失效；中断后可续跑，失败不能被计为成功缓存。
- 机制开关在适当构造案例上有预期效果；实际预算与 token 计数可核验。
- 每项正式图表均可从逐样本记录重建；数据行数、分母和失败数可核对。
- 使用必要的离线测试及小样本真实验证，不用模拟回答代替真实实验结果。
- 不以分数必须超过基线或接近论文为验收标准；负面结果同样保留并解释。
